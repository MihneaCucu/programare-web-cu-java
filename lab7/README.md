
# Lab 7 - JDBC & JdbcTemplate

## Overview

In this laboratory, we will connect our Event Planner Spring Boot
application to a PostgreSQL database.

In previous laboratories, events were stored in an in-memory
ArrayList. We will now use a relational database to persist data.

We will explore:

- JDBC fundamentals
- Connection, PreparedStatement and ResultSet
- Parameterized SQL queries
- try-with-resources
- Spring JdbcTemplate
- RowMapper
- SQL operations (SELECT, INSERT, UPDATE, DELETE)
- Integration with an existing REST API

## Prerequisites

Before starting, make sure you have:

- Java 21
- IntelliJ IDEA
- PostgreSQL (version 18 recommended)
- pgAdmin 4
- Maven (the project includes a Maven Wrapper)

PostgreSQL download:
https://www.postgresql.org/download/windows/

### PostgreSQL Installation

On Windows:

1. Open the PostgreSQL download page.
2. Download the Windows installer.
3. Run the installer.
4. Select the following components:
    - PostgreSQL Server
    - pgAdmin 4
    - Command Line Tools
5. Stack Builder is optional and is not required.
6. Keep the default port: 5432.
7. Set a password for the PostgreSQL user `postgres`.
8. Complete the installation.

Remember your PostgreSQL password. You will need it when
configuring the Spring Boot application.

Note: The pgAdmin master password, if requested, is different
from the PostgreSQL database user's password.

## 1. Database Setup

We will use a PostgreSQL database named `eventdb`.

### 1.1 Create the Database

1. Open pgAdmin 4.
2. Connect to your local PostgreSQL server.
3. Expand Servers -> PostgreSQL.
4. Right-click Databases -> Create -> Database.
5. Enter the database name: `eventdb`.
6. Keep `postgres` as the owner.
7. Click Save.

### 1.2 Create the Events Table

The project includes the SQL script:

    database/schema.sql

To execute it:

1. Select the `eventdb` database in pgAdmin.
2. Open Query Tool.
3. Open `database/schema.sql` from this project.
4. Copy its contents into Query Tool.
5. Execute the SQL statement (F5).

The script creates the `events` table with:

- id: unique identifier generated by PostgreSQL
- name: event name
- category: event category

### 1.3 Insert Sample Data

The project also includes:

    database/data.sql

Execute this script in Query Tool to insert three events:

| ID | Name | Category |
|----|------|----------|
| 1 | Java Workshop | Technology |
| 2 | Spring Boot Lab | Education |
| 3 | REST Workshop | Technology |

The IDs shown above assume a fresh database.

Important: Run the insert script only once on a fresh table.
Running it multiple times will create duplicate events.

The scripts in the `database/` folder are executed manually
in pgAdmin. Spring Boot does not automatically execute them.

### 1.4 Verify the Database

In pgAdmin Query Tool, execute:

```sql
SELECT * FROM events ORDER BY id;
```

You should see the three inserted events.

## 2. Spring Boot Configuration

### 2.1 Project Dependencies

The `pom.xml` already contains the required dependencies:

- Spring Boot Web MVC
- Spring JDBC
- PostgreSQL JDBC Driver
- Spring Boot Validation

The PostgreSQL driver allows Java to communicate with
PostgreSQL.

Spring JDBC provides JdbcTemplate.

### 2.2 Database Connection

Open:

    src/main/resources/application.properties

The datasource configuration is:

```properties
spring.application.name=lab7

spring.datasource.url=jdbc:postgresql://localhost:5432/eventdb
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD}
```

Configuration details:

- `localhost`: the database runs on your computer.
- `5432`: the default PostgreSQL port.
- `eventdb`: the database created previously.
- `DB_USERNAME`: optional environment variable.
- `postgres`: default username if DB_USERNAME is not defined.
- `DB_PASSWORD`: required environment variable.

You can use the default PostgreSQL user `postgres`
for this local laboratory.

### 2.3 Configure Environment Variables in IntelliJ

1. Open Run -> Edit Configurations.
2. Select or create the run configuration for `Lab7Application`.
3. Find the Environment variables section.
4. Add the following variable:

   DB_PASSWORD=your_postgresql_password

Replace `your_postgresql_password` with the password
you configured during PostgreSQL installation.

If you use a different PostgreSQL user, also add:

    DB_USERNAME=your_username

Otherwise, the application automatically uses `postgres`.

Important:
- Do not add actual passwords to application.properties.
- Do not commit passwords to GitHub.
- Do not share your environment variables or credentials.

### 2.4 Run the Application

Run `Lab7Application` from IntelliJ.

Alternatively, from the `lab7` directory, on Windows:

```powershell
.\mvnw.cmd spring-boot:run
```

Make sure DB_PASSWORD is configured in the environment
used to start the application.

The REST API starts at:

    http://localhost:8080

The starter project should compile and start without
activating any optional demo profile.

Some REST operations will not work until you implement
the repository methods in the following exercises.

## 3. Exercise 1 - JDBC Fundamentals

### Objective

Learn how Java communicates with a relational database
using standard JDBC interfaces.

### File

    src/main/java/ro/example/lab7/JdbcDemoRunner.java

The class already contains:

- Spring's @Component annotation
- A DataSource dependency
- Constructor-based dependency injection
- CommandLineRunner
- TODO comments

### Tasks

1. Obtain a Connection from the DataSource.
2. Create a PreparedStatement to select an event by ID.
3. Use a parameterized SQL query with `?`.
4. Bind the event ID using `setLong()`.
5. Execute the query and obtain a ResultSet.
6. Read the ID, name and category from the result.
7. Display the event in the console.
8. Handle the case when the event does not exist.
9. Use try-with-resources to close JDBC resources.

Example SQL query:

```sql
SELECT id, name, category
FROM events
WHERE id = ?;
```

Remember: JDBC parameter indexes start at 1.

### Testing

Activate the Spring profile:

    jdbc-demo

See Section 8 for profile configuration instructions.

Run the application.

After completing the TODOs, the console should display
the requested event or a message indicating that the
event was not found.

### Discussion

- What is a DataSource?
- What is the role of Connection?
- Why should we use PreparedStatement?
- What is a ResultSet?
- Why is try-with-resources useful?
- How do parameterized queries help prevent SQL Injection?

## 4. Exercise 2 - Spring JdbcTemplate

### Objective

Use Spring JdbcTemplate to simplify database access.

### File

    src/main/java/ro/example/lab7/repository/EventRepository.java

The repository already contains:

- The @Repository annotation
- Constructor-based dependency injection
- An injected JdbcTemplate instance
- Method signatures and TODO comments

### Task 1 - Implement findAll()

Implement:

    List<Event> findAll()

Requirements:

- Execute a SELECT query that retrieves all events.
- Use `jdbcTemplate.query()`.
- Use a RowMapper to convert each database row
  into an Event object.
- Return a List<Event>.

Suggested SQL:

```sql
SELECT id, name, category FROM events;
```

### Task 2 - Implement findById()

Implement:

    Optional<Event> findById(long id)

Requirements:

- Select an event by ID.
- Use a parameterized SQL query.
- Map the result to an Event object.
- Return Optional.empty() if the event does not exist.

Suggested SQL:

```sql
SELECT id, name, category
FROM events
WHERE id = ?;
```

### Testing

After implementing both methods, activate:

    template-demo

The `JdbcTemplateDemoRunner` class already contains
sample calls to the repository.

The console should display:

- The number of events found.
- The name of the event with ID 2, if it exists.

### Discussion

Compare standard JDBC with JdbcTemplate.

Which implementation requires less boilerplate code?

Who manages JDBC connections and resource cleanup
when using JdbcTemplate?

What is the role of RowMapper?

## 5. Exercise 3 - Database Operations

### Objective

Implement database operations using JdbcTemplate
and parameterized SQL.

Continue working in:

    EventRepository.java

### Task 3 - Implement save()

Implement:

    Long save(String name, String category)

Requirements:

- Insert a new event.
- Use parameterized SQL.
- Let PostgreSQL generate the event ID.
- Return the generated ID.

Suggested PostgreSQL query:

```sql
INSERT INTO events (name, category)
VALUES (?, ?)
RETURNING id;
```

Hint: `queryForObject()` can retrieve the generated ID
from PostgreSQL's RETURNING clause.

### Task 4 - Implement updateById()

Implement:

    int updateById(long id, String name, String category)

Requirements:

- Update the event identified by its ID.
- Use `jdbcTemplate.update()`.
- Return the number of affected rows.

Suggested SQL:

```sql
UPDATE events
SET name = ?, category = ?
WHERE id = ?;
```

### Task 5 - Implement deleteById()

Implement:

    int deleteById(long id)

Requirements:

- Delete the event identified by its ID.
- Use `jdbcTemplate.update()`.
- Return the number of affected rows.

Suggested SQL:

```sql
DELETE FROM events WHERE id = ?;
```

### Discussion

- What is the difference between query() and update()?
- What does update() return?
- How does PostgreSQL generate IDs?
- Why do we use parameters instead of SQL concatenation?

## 7. Testing the REST API

Use the `requests.http` file in IntelliJ IDEA.

Make sure the application runs without a demo profile.

### Main Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | /api/events | Get all events |
| GET | /api/events/{id} | Get an event by ID |
| GET | /api/events?category=Technology | Filter by category |
| GET | /api/categories | Get all categories |
| GET | /api/events/summary | Get event statistics |
| POST | /api/events | Create an event |
| PUT | /api/events/{id} | Update an event |
| DELETE | /api/events/{id} | Delete an event |
| GET | /api/client-info | Read a custom header |

### Example GET

```http
GET http://localhost:8080/api/events
Accept: application/json
```

### Example POST

```http
POST http://localhost:8080/api/events
Content-Type: application/json

{
  "name": "PostgreSQL Workshop",
  "category": "Technology"
}
```

A successful POST returns HTTP 201 Created
and includes the generated event ID.

Use that ID when testing PUT and DELETE.

### Validation

The existing REST API validates event data.

Try sending:

- An empty event name.
- An event name shorter than 3 characters.
- An empty category.

Invalid requests should return HTTP 400 Bad Request.

Requesting an event that does not exist should
return HTTP 404 Not Found.

### Verify Persistence

In pgAdmin, execute:

```sql
SELECT * FROM events ORDER BY id;
```

Verify that INSERT, UPDATE and DELETE operations
are reflected in PostgreSQL.

## 9. Troubleshooting

### Database Connection Failed

Check that:

- PostgreSQL is running.
- The database `eventdb` exists.
- The configured port is 5432.
- The username is correct.
- DB_PASSWORD contains the correct PostgreSQL password.

### Table Does Not Exist

Make sure you executed:

    database/schema.sql

in the `eventdb` database.

### No Events Found

Execute:

    database/data.sql

once, if the table is empty.

### UnsupportedOperationException

Some repository methods contain TODOs.

This is expected until you implement them.

### Port 8080 Already in Use

Stop any other Spring Boot application that uses
port 8080 before starting Lab7Application.
